## ADR-001：采用 L3（本机 REST 源 + 服务时 URL 改写）

**状态**：**已废弃**（2026-11-01，由 ADR-013 取代）。本节保留，因为下面这张否决表是
"为什么绕不开 TLS 终止"的完整推理，切换架构时仍需它来判断哪些替代方案依然不可取。

**决定**：在本机 `127.0.0.1` 上运行一个 winget REST 源，服务端把清单里的
`InstallerUrl` 动态改写为加速器地址。

**被否决的替代方案**：

| 方案 | 提权 | 安全基线影响 | 透明性 | winget 记账 | 否决理由 |
|---|---|---|---|---|---|
| **L1** 本地清单改写 + `winget install -m` | 1 次 | **明显下降** | 半透明 | ✅ | 需启用 `LocalManifestFiles`，等于让本机**任意程序**都能静默安装任意本地清单；且每次必须走包装器，`winget upgrade --all` 会绕过它 |
| **L2** 自己下载 + 自己装 | 无 | 不变 | 否 | ❌ | 丢失 `winget list` 记账与升级链；静默参数需自行维护 |
| **L4** MITM + `--proxy` | 1 次 + 根证书 | **最严重** | ✅ | ✅ | 根证书可签发任意域名；且 `--proxy` 也需 `ProxyCommandLineOptions` 提权 |
| **L5** hosts 劫持 + 伪冒证书 | 1 次 + 证书 | **最严重** | ✅ | ✅ | 破坏全机对相关 host 的访问，需覆盖多个域名 |
| **L7** 本机并发下载 | 无 | 不变 | 否 | ❌ | **实测触发 CDN 惩罚，导致该 IP 全部发布资产下载归零** |

**2026-11-01 补注**：上表否决 L4 的两条理由是"根证书可签发任意域名"与"`--proxy` 也需提权"。
现在的架构与 L4 的差别恰好落在这两点上——CA 用 `NameConstraints` 限定到 4 个 host（ADR-014），
且用 PAC 而不是 `--proxy`，所以不需要提权。**L5（hosts 劫持）与 L1（本地清单）仍然否决**，
它们没有任何约束能变得可接受。

**理由**：
1. 三种"必须提权"的方案里，L3 的副作用最小——只新增一张仅用于 `localhost` 的证书，
   不改动任何 winget 安全策略
2. 唯一**完全透明**的方案：`winget search/install/upgrade` 全部照常工作
3. 顺带解决源层偶发 4–81 秒的查询延迟
4. 哈希仍来自官方清单（见 ADR-004 与调研 6.2）

**代价**：需要常驻一个本地服务；需要一次性提权；依赖清单同步。

## ADR-002：不以 `cf-winget-proxy` 为基础

**状态**：仍有效。结论不变；其中第 2 条"改写全部 host"的反面教材，
在新架构里直接体现为"PAC 只圈 4 个 host，其余 DIRECT"（ADR-014）。

**决定**：不复用、不 fork。

**理由**（均为实测/核查结论）：
1. **无 LICENSE 文件** → 默认 All rights reserved，**法律上不可复用**
2. **改写全部 host**：连 Firefox 的 Mozilla CDN 也经它的 Worker，零收益、徒增风险
3. 健康度存疑：0★ / 1 fork，创建与最后推送同为 2026-05-27，无 README/issues/homepage
4. 第二个域名 `winget.cn.lihongjie.cn` TLS 失败
5. 架构上是公网 Worker，与"纯本机"目标相反

## ADR-003：自行实现，而非直接分发 rewinged

**状态**：**部分作废**（2026-11-01）。"自己实现、不直接分发"仍成立；
"参考其协议实现与模型组织"作废——新架构不实现协议，见 ADR-011。

**决定**：自己写代码，参考 rewinged（MIT）的协议实现与模型组织。

**理由**：
1. rewinged 的目标是**企业内网/离线分发**，不是加速；它的 `autoInternalize`
   假设"服务端有好网络"，与我们的场景相反（见 `rewinged-reference.md`）
2. 我们只需要它最核心的一条行为（"读目录 → 原样经 REST 输出"），
   其余企业特性（Entra ID、trustedProxies）全部不需要
3. 它是 **pre-1.0**，作者明示配置与行为可变；自实现可控制演进
4. 我们的核心增量（host 白名单改写 + 加速器健康检查 + 失败回退）它没有

**代价**：承担协议实现的正确性责任。缓解：以 MIT 方式参考其代码并保留声明。

## ADR-004：只改写白名单内的 host

**状态**：**仍有效**（2026-11-01 起作用点变化）。"白名单"仍是本项目的核心边界，
但对象从"清单里的 `InstallerUrl` host"变成"代理层的 CONNECT host"；
两个白名单现在是同一份，见 ADR-014 约束 2。

**决定**：配置提供"host → 加速器前缀"映射，**只有命中白名单的 URL 才改写**，
其余原样透传。

**默认白名单**（待实现时按真实数据补齐）：

```
github.com
objects.githubusercontent.com
codeload.github.com
release-assets.githubusercontent.com
```

**理由**：
1. 只有这些 host 在国内慢（实测数据）
2. `cf-winget-proxy` 的全量改写是明确的反面教材——把快流量也塞进代理
3. 白名单可配置，便于用户按自己的网络状况调整

**代价**：需覆盖 GitHub 未来的新资产域名；漏配时该包会退化到直连（慢但可用）。

## ADR-005：服务时改写，不落盘改写

**状态**：**已废弃**（2026-11-01）。已无清单可落盘；
"改写不落盘、配置驱动、换加速器无需重建数据"这条原则被 ADR-013 完整继承——
改写发生在代理转发时，磁盘上不产生任何副本。

**决定**：磁盘上的清单保持与上游完全一致；改写发生在 HTTP 响应生成时。

**理由**：
1. 换加速器、加/减 host 只需改配置，**无需重新同步清单**
2. 本地清单可随时与上游做 `diff` 校验完整性（若落盘改写则无法区分"我们的改动"和"上游的改动"）
3. 加速器失效时可立即回退到原始 URL，无需回滚文件

**代价**：每次响应都要做一次字符串/结构改写（成本可忽略）。

## ADR-006：内置下载逻辑并发上限 4–8，且必须走加速器

**状态**：仍有效，但**适用范围改变**（2026-11-01）。本项目不再主动下载任何内容
（winget 自己下载，我们只转发），因此原条款的直接对象消失；
约束转移到代理并发与健康探测：探测并发上限 1、探测间隔 ≥5 分钟（`design.md` §8）。

**决定**：项目中任何主动下载（清单同步骤除外）并发不超过 8，默认 4，
必须带指数退避与随机分片。

**理由**：实测 32–64 并发会导致 GitHub 资产 CDN 对本机 IP 施加惩罚，
且惩罚**外溢**到正常使用（详见 `research.md` 第 4 节）。

**代价**：放弃"靠并发免费提速"的幻想，依赖加速器。

## ADR-007：不启用 `LocalManifestFiles`、不装根证书、不改 hosts

**状态**：**已收窄**（2026-11-01）。"不装根证书"不再绝对成立：
在 ADR-014 的三重约束下，接受一张**带 Name Constraints**的 CA 装入 `CurrentUser\Root`。
`LocalManifestFiles` 与 hosts 仍然不做——这两项没有任何约束能把它变得可接受。

**决定**：项目不要求用户做以上任何一项。

**理由**：这三项分别对应"任意本地清单可静默安装"、"任意域名可被伪造"、
"全机域名解析被改写"，都是**机器级安全基线下降**，
为一个下载加速需求付这种代价不成比例。

**代价**：功能上限受限（见 ADR-001 的取舍）。

## ADR-008：清单版本支持范围

**状态**：**已废弃**（2026-11-01，新架构不投影清单，本议题整体消失）。
原判定过程保留如下——它记录了"版本维度是双向的"这个后来促成架构切换的认识。

**当时的结论**：原为"待定"；2026-11-01 复核后**已确定**（依据见 `verification-2026-11-01.md` §3.3–3.4）。

**背景**：rewinged 同时支持清单 schema **1.1.0 – 1.10.0**，其 `models/` 目录
为此有 8 个版本的模型文件，合计约 **200 KB**（占其代码 342.8 KB 的六成）。

**原选项**：

| 选项 | 代码量 | 原判断风险 |
|---|---|---|
| A. 全版本（照 rewinged） | ~200 KB 模型 | 低（兼容性好），维护重 |
| B. 仅当前 winget 使用版本（1.10.0）+ 1.9.0 兜底 | ~50 KB | 中（winget 升级后可能失效） |
| C. 只做 1.10.0 | ~26 KB | 高 |

**原倾向**：先做 **B**，把版本处理抽象成可插拔，后续按需补。

**复核结论**：

1. 协商机制已查明。客户端 `RestClient::GetLatestCommonVersion()` 对
   "服务端 `ServerSupportedVersions`"与"客户端支持集"取**交集再取最大值**；
   客户端支持集为 `1.0.0 / 1.1.0 / 1.4.0 / 1.5.0 / 1.6.0 / 1.7.0 / 1.9.0 / 1.10.0 / 1.12.0 / 1.28.0`。
   **服务端只声明 `["1.10.0"]` 时，客户端必然回落到 1.10.0，不会拒绝连接。**
2. 因此原表对 C 的"风险高"**下调为中低**：残余风险只剩下"客户端版本过旧、不支持 1.10.0
   导致协商失败"，由 `doctor` 检查 winget 版本并给明确报错即可兜住。
3. **但原表低估了工作量**：版本维度是**双向**的。输出只做 1.10.0，仍然必须把
   `winget-pkgs` 里横跨多个 schema 版本的 YAML **读进来**，再转换成 1.10.0 形状。
   那 ~200 KB 模型中有相当一部分是**读取侧**成本，不是输出侧。

**决定（修订）**：采用 **C′ —— 输出契约只做 1.10.0，且读侧不按版本建 struct**。

- 读侧：YAML → 通用树（`map` / `any`），不对应任何 schema 版本
- 转换：一张"跨 schema 字段改名/新增映射表"
- 输出：投影成 1.10.0 JSON，由单一 `ManifestCodec` 负责

**理由**：

1. 契约只需一个版本，协商安全性已证明（上面第 1 点）
2. 通用树把"8 份模型 ≈ 200 KB"压成"一张映射表 + 一个投影函数"，
   且**天然支持任意新版本清单**——上游加字段只需补映射，不需要新代码
3. 与 ADR-003 一致：借鉴 rewinged 的**字段语义**，不搬它的模型体系

**代价与风险**：

- 需一次性穷举跨版本改名/新增字段（`AppsAndFeaturesEntries`、`Markets`、
  `InstallerSha256` 一系等）；**漏掉的字段会被静默丢弃**，这是本方案最危险的地方
  → 必须配 fixture 测试（`verification-2026-11-01.md` V6），不能靠人工 `winget show`
- 1.10.0 中不存在的字段会被截断，这是"最小集"的固有代价
- 若将来 winget 的必需字段只在新契约中提供，需重新评估

**回退路径**：若映射表维护成本超出预期，退回 A（照搬 rewinged 的多版本模型），
接口不变（`ManifestCodec`），改动局限在实现层。

## ADR-009：实现语言

**状态**：**仍定 Rust**（2026-11-01 第四次修订）。交付语言不变；
新增一笔变更：Python 因架构验证的需要先以**原型**形式存在，但不进交付产物（ADR-015）。

**变更史**（真正重要的是最后一列的"判据"，不是结论）：

| # | 语言 | 触发条件 | 失效原因 |
|---|---|---|---|
| 1 | Go（初稿） | 与参考对象同语言，"移植成本最低" | ADR-008 改为 C′ 后不再移植模型，理由消失 |
| 2 | Python + uv（复核后） | 本机已有 `uv`、零安装、性能不敏感 | 隐含前提"只自己用"被推翻 |
| 3 | **Rust** | **明确要产出单文件二进制对外分发** | — |
| 4 | **Rust（维持）**；Python 仅作原型 | 新架构要在进程内终止 TLS、签发证书，风险未知处先用原型验证 | 原型不进交付：误报率高、启动慢、需运行时（ADR-015） |

**判据**（环境一变就重评，不凭偏好）：

1. **谁长期维护**（交接成本）→ 自己维护，故不构成 Go/C# 的加分项
2. **依赖选型**是否逐条可解释（ADR-012）
3. **Windows 系统集成**在关键路径上的权重 → 证书库是 `cert` / `setup` 的必经路径

三条全指向 Rust。

**为什么是 Rust**：

1. **`windows-rs` 正好压在本项目唯一的系统集成层上**：证书存储
   （`CertOpenStore` / `CertAddEncodedCertificateToStore`）、注册表（HKCU Run）、提权检测。
   Go 的 `x/sys/windows` 是裸 syscall，需自封一层或转调 PowerShell。
2. **类型系统能把"只改 `InstallerUrl`"变成编译期不变量**：newtype 区分
   `OriginalUrl` / `RewrittenUrl`、字段私有、只留一个转换函数。本项目的核心卖点是
   哈希信任链不变，Go 只能靠测试断言加人工评审。
3. **产物 4–6 MB**，`+crt-static` 后零依赖（不需要 VC++ 运行库）；Go 约 11–13 MB。
   用户恰在慢速网络上，体积是真实成本。
4. **T2 边界更安全**（ADR-011）：跨语言重写天然不会滑向"搬运"；
   同语言 + 同 workload 则极易趋同。
5. **不需要异步**：本地单用户、并发 1–2，同步代码足够，`async` 与 borrow 纠缠的场景基本不出现。

**实测支撑**（工具链可达性，2026-11-01）：

| 源 | 结果 |
|---|---|
| `rsproxy.cn`（dist） | **200 / 0.58 s** |
| `mirrors.ustc.edu.cn/rust-static` | 200 / 1.47 s |
| `static.rust-lang.org`（官方） | 200 / 12.0 s |
| `index.crates.io` / `static.crates.io` | 200 / 3.57 s、1.60 s |
| 本机 MSVC | ✅ 14.51.36231 + Windows SDK 10.0.26100.0（VS Enterprise 2026） |

官方源慢，但国内镜像比 Go 官方源（`dl.google.com` 3.0 s）**还快** ⇒ 工具链不构成阻碍。
（初稿曾以"工具链慢"排除 Rust，那是没测镜像就下的判断，已作废。）

**为什么不选其它**：

| 语言 | 否决点（针对本项目） |
|---|---|
| Go | 系统集成层要自封 syscall；与参考同语言，T2 边界易破；体积 11–13 MB |
| Python | **PyInstaller 产物杀软误报率高**——一个"要帮用户装软件"的工具被 Defender 拦下，信任直接归零；产物运行时解包到 temp、启动 1–3 s |
| C# | NativeAOT 与 YamlDotNet 的反射冲突；非 AOT 自包含约 70 MB，对慢网用户不友好；本机无 .NET SDK |

**硬约束**（违反即重议）：

- 依赖选型约束见 **ADR-012**
- TLS 用 `rustls`（纯 Rust、静态链接友好），**不用** `native-tls`
- ~~同步子命令用 `std::process::Command` 调系统 `git.exe`，不用 `git2`~~
- ~~YAML 用 `serde_yaml_ng`~~
- 发布 `x86_64-pc-windows-msvc` + `-C target-feature=+crt-static` + strip + LTO

> 2026-11-01：划掉的两条随架构切换取消（不再同步清单、不再解析 YAML），
> 见 ADR-012「架构切换后的调整」。`rustls` 与发布参数仍然有效，且 `rustls` 升为核心依赖。

**代价**：编译比 Go 慢（首次含依赖 1–2 min，增量 5–20 s）；第三方读者读 Go 更容易；
`serde_yaml` 生态分裂需显式锁定。

**何时重审**：若需交给不熟 Rust 的人维护，或依赖面失控到 >40 个 crate。

## ADR-010：不实现 rewinged 的企业特性

**状态**：**已废弃**（2026-11-01）。前提消失——本项目不再实现任何协议端点，
这些"要不要实现企业特性"的选择题没有了。

**决定**：不实现 Entra ID 认证、`trustedProxies`、`autoInternalize`。

**理由**：本地单用户场景无意义；`autoInternalize` 与"不落地安装包"的目标直接冲突。

**代价**：不能用于多用户共享的内网源——但那不是本项目目标。

## ADR-012：依赖选型约束

**状态**：**第 4 次修订 / 2026-11-01**——**取消数量上限**。

**决定**：**不设依赖数量上限。** 每个直接依赖必须在 ADR 或提交说明里逐条写明
"为什么不能用标准库或已有依赖实现"；禁止清单仍然有效。

**理由**：本工具要求用户**信任**它改写安装源。一个自身带 80 个第三方 crate 的工具，
逻辑上自相矛盾；且依赖越多，`cargo audit` 噪音越大、构建越慢、攻击面越广——
对"能改写安装源的工具"来说，供应链攻击的收益极高，这是必须主动收敛的风险。

**禁止清单**：

| 依赖 | 原因 | 替代 |
|---|---|---|
| `tokio` / `axum` / `actix-web` / `hyper` | 本地单用户、并发 1–2，异步是过度设计 | `std::net::TcpListener` + 最小 HTTP/1.1 |
| `git2` / `libgit2-sys` | 引入 C 工具链与 cmake 依赖 | `std::process::Command` 调系统 `git.exe` |
| `native-tls` / `openssl` | 系统依赖、静态链接困难 | `rustls` + `rustls-pemfile` |
| `serde_yaml` | **上游已归档停维护** | `serde_yaml_ng` |
| `reqwest`（默认特性） | 拖入 tokio 与整套 TLS 栈 | 健康探测用 `TcpStream` + `rustls`，或最小 HTTP 客户端 |

**允许的直接依赖**（预估，以实测为准）：`serde`、`serde_json`、`serde_yaml_ng`、
`rustls`、`rustls-pemfile`、`windows`（限 feature）、`anyhow` 或 `thiserror`（二选一）。

**手写最小 HTTP 的边界**：

- 必须按 `Content-Length` 读请求体（`POST /manifestSearch` 带 JSON）
- 支持 `Connection: keep-alive`；错误体为固定 JSON（404 / 500）
- **不实现 chunked 请求体**——但必须先确认 winget 客户端不发 chunked（发则改为支持）
- 不实现 HTTP/2、压缩、multipart

**`windows` crate 的 feature 白名单**：`Win32_Security_Cryptography`、
`Win32_System_Registry`、`Win32_Foundation`、`Win32_System_Threading`（提权检测）。
不得为省事开启 `windows` 全量 feature。

**检查方式**：CI 统计 `cargo tree` 数量，超阈值失败。

### 架构切换后的调整（2026-11-01）

变化只在"哪些依赖是核心"：

| 项 | 变化 | 理由 |
|---|---|---|
| `rustls` + `rustls-pemfile` | **升为核心依赖** | 代理要终止 TLS，这是关键路径 |
| `rcgen`（或等价的证书生成 crate） | **新增允许** | 生成自签 CA 与叶证书、写 `NameConstraints`。若 `rcgen` 无法表达 Name Constraints，改用 `x509-cert` 系（**未验证**，阶段 2 首要确认） |
| `std::thread` | **允许** | 并发度是"每连接一线程"级别；不需要异步运行时来管理几百个连接之外的任何事 |
| `serde` / `serde_json` | 保留 | 配置解析 |
| `serde_yaml_ng` | **取消** | 不再读清单 YAML |
| 系统 `git.exe`（`std::process::Command`） | **取消** | 不再同步清单 |
| `tokio` / `axum` / `hyper` / `actix-web` | **仍禁** | 同步阻塞 I/O + 线程已经把问题解决干净；引入异步运行时只会扩大审计面（ADR-014 要求用户信任本工具改写安装流量） |
| `native-tls` / `openssl` | **仍禁** | 同上，且静态链接困难 |
| `reqwest`（默认特性） | **仍禁** | 健康探测只需要一次 HTTP HEAD/GET，`TcpStream` + `rustls` 足够 |
| `webpki-roots` | **新增允许** | 上游（加速器）证书校验需要根证书。纯数据 crate，无传递依赖、无 C 代码。纯新增，理由逐条可查 |
| `rcgen` 版本 | **钉 0.14** | 0.14 才有 `Issuer::from_ca_cert_pem`，能把磁盘上已有的 CA 重新当作签发者；0.13 做不到，会导致每次重启换一张 CA、用户必须重新信任 |

> **已确认（2026-11-01）**：`rcgen` 0.14 能表达 Name Constraints
> （`NameConstraints { permitted_subtrees: Vec<GeneralSubtree>, excluded_subtrees }`，
> 且 `GeneralSubtree::DnsName` 正好对应我们需要的 4 个域名）。
> 上面「若 `rcgen` 无法表达 Name Constraints，改用 `x509-cert` 系」这条待验证项**关闭**，
> 不需要 `x509-cert`。

### 为什么取消数量上限（2026-11-01）

原规则是「直接依赖 ≤ 8、传递依赖 ≤ 30」，并在此前被突破过一次（传递依赖实测 47 个，
上限临时改成 ≤ 50）。复盘后确认**这条规则本身没有依据**：

- 它没有来自外部的要求（无安全审计规范、无合规约束），是本项目自己拍的数字；
- 数字被随手改过一次，说明它不承载真实约束；
- 它在此后**阻碍了正确的技术选择**：为了守住"不加第 9 个依赖"，
  一度考虑手写 SHA-1；而正确做法是直接用 `windows-sys` 的 Win32 证书 API。

**保留的部分**：依赖必须**逐条可解释**。这条才是目的——控制审计面靠的是
"每个依赖都说得出理由"，不是数个数。禁止清单（`tokio` / `native-tls` / `reqwest` 等）
仍然有效，因为它们各自有明确的技术理由。

**当前实测**：直接依赖 8 个、唯一 crate 55 个（含传递）。变化时应更新此数字，
但**不设阈值**，也不需要为超标写说明。

**手写 HTTP 的边界（调整后）**：

- 必须正确解析 `CONNECT host:port`，且**不能越过头部边界读走 ClientHello**（原型为此逐字节读）
- 生效的请求头必须原样透传：`Range`、`If-Range`、`If-None-Match`、`User-Agent`
- 必须剥离逐跳头：`Proxy-Connection`、`Connection`、`Keep-Alive`、`TE`、`Trailer`、`Upgrade`
- 响应体三态都要处理：`Content-Length` / `Transfer-Encoding: chunked` / 无长度（读到 EOF）
- 仍不实现 HTTP/2——不协商 ALPN，强制 HTTP/1.1（原型即如此，实测 winget 接受）

## ADR-013：架构切换——PAC + 本机 MITM 改写代理

**状态**：**现行主架构**（2026-11-01，取代 ADR-001）。

**背景**：ADR-001 的 REST 源方案要求同步 1 GB 级清单、做跨 schema 投影（ADR-008）、
实现 7×9 的 `manifestSearch` 语义——复杂度都花在"重造一个能替代官方源的源"上。
而真正要解决的问题只有一个：**安装包下载慢或断**。

2026-11-01 的两次实测（`verification-proxy-2026-11-01.md` §2 用 mitmproxy、§9 用原型）
证明：在下载层做代理改写即可解决，且不需要清单、不需要注册源、不需要管理员。

**决定**：不实现 REST 源。改为本机代理：

1. **PAC** 只把 4 个 host（`github.com` / `objects.githubusercontent.com` /
   `codeload.github.com` / `release-assets.githubusercontent.com`）指向 `127.0.0.1:8443`
2. 代理对命中白名单的 `CONNECT` **终止 TLS**（用 ADR-014 约束的 CA 签叶证书），
   把请求改写成 `https://<加速器>/<原始完整 URL>`
3. 其余 host 一律**原样隧道**，不改写
4. winget 的清单查询仍走官方源，**完全不经过本项目**

**与旧方案的对比**：

| 维度 | A：REST 源（ADR-001） | **B：代理层（本 ADR）** |
|---|---|---|
| 清单同步 | 1 GB 级，需增量策略 | **无** |
| schema 投影 / 版本映射表 | 必需（ADR-008） | **无** |
| `manifestSearch` 语义（7×9） | 必需 | **无** |
| 协议端点 | 3 个 | **0 个** |
| 与官方源重复 id / 共存策略 | 存在，且 `source add` 无 `--priority` | **不存在**（不改源） |
| 覆盖范围 | 受同步范围限制 | 所有经这 4 个 host 的下载 |
| 需要管理员 | 必需（`source add`） | **不需要**（HKCU + `CurrentUser\Root`） |
| 与 Microsoft 域的关系 | 替代其源 | **完全不碰** |
| 代码量 | 3000+ 行（估） | 300–500 行（原型为 400 行 + 182 行 CA） |
| 新增信任 | 仅 `localhost` 的证书 | 带 Name Constraints 的 CA（ADR-014） |
| 失效时的影响 | 该源不可用 | PAC 圈定的 4 个 host 失败，其余不受影响 |

**理由**：

1. 问题边界就在下载层，代理层是同等效果下更小的机制
2. 不注册源 ⇒ 不与官方源争 id、不需要管理员、不受 `ServerSupportedVersions` 约束
3. 覆盖范围自动等于"所有 GitHub 托管的安装包"，不需要维护清单，也不会过期
4. **完整性不变**：winget 仍用官方清单的 `InstallerSha256` 校验字节（实测通过，§9.1）

**代价**：

1. 引入 TLS 终止——这正是 ADR-007 当初否决的东西，靠 ADR-014 的三重约束收敛
2. **代理是单点**：进程挂了，被 PAC 圈入的 4 个 host 会失败（用 PAC 而非全局 `ProxyServer`
   正是为了把爆炸半径限制在这 4 个 host，§9.3）
3. 依赖第三方公共加速器（当前仅 `gh-proxy.com` 可用）
4. 需要一次根证书安装的交互确认（§10）

**何时重审**：winget 改变下载路径或不再使用系统 PAC；加速器全部失效；
系统策略禁止用户级根证书或 PAC。

## ADR-014：安全边界——三重约束

**状态**：**现行**（2026-11-01，收窄 ADR-007）。

单说"我们要 MITM"是不可接受的（ADR-007 的原判断仍然成立）。可接受的形态必须**三条同时成立**，
缺一条就退回 ADR-001：

| # | 约束 | 实现方式 | 实测证据 |
|---|---|---|---|
| 1 | CA 只能签 4 个域名 | `NameConstraints permitted_subtrees` = 4 个 DNS + `path_length=0` | §9.4：签 `example.com` 被客户端拒绝（`SSLV3_ALERT_CERTIFICATE_UNKNOWN`） |
| 2 | 代理只被这 4 个 host 使用 | PAC 只对 4 个 host（含 `*.github.com`）返回 `PROXY`，其余 `DIRECT`；`ProxyEnable=0` | §9.3：`PAC-SERVED` ×9；非白名单 host 隧道 200 / 0.96 s |
| 3 | 字节被改会被发现 | winget 用官方清单的 `InstallerSha256` 校验；本项目只改请求 URL，**不碰响应体** | §9.1：`"已成功验证安装程序哈希"` |

**为什么这三条足够**：MITM 在这里能影响的只有"谁能看到你在下载什么"（全是公开安装包），
不能影响"你下载到的是什么"——因为哈希锚定在 Microsoft 的清单里，与我们的 CA 无关。

**残余风险**（按严重度，不掩饰）：

| 风险 | 说明 | 缓解 |
|---|---|---|
| CA 私钥可在**这 4 个 host 上**冒充 | 约束 1 限定范围，不限定"范围内不许冒充" | 私钥 ACL 限当前用户；CA 有效期 365 天；卸载即删；CA 私钥加密存储（阶段 4） |
| 代理进程可被替换或劫持 | 与其它同权限本地进程同级 | 与本项目"用户信任它改写流量"的前提同源，不额外引入 |
| 根证书常驻 | 忘记卸载则长期有效 | `teardown` 强制删除并自校验（阶段 4） |
| 内容保密性下降 | 代理可见下载内容 | 无需缓解：公开分发物 |

**明确不做**：

- 不代理 `microsoft.com` / `windowsupdate.com` 等系统域（PAC 不涉及，§9.3 已验）
- 不改 hosts、不改 DNS、不启用 `LocalManifestFiles`、不需要 `--proxy` 管理员开关
- 不把 CA 私钥写入日志或仓库（`.gitignore` 已排除 `*.pem` / `*.key`）

**回退条件**：任何一条约束无法成立（例如 `rcgen` 无法写 Name Constraints，或 Windows 某版本
不再强制校验 Name Constraints），必须退回 ADR-001。

## ADR-015：交付路线——Python 原型 → Rust 单文件二进制

**状态**：**现行**（2026-11-01）。

**决定**：

1. `prototype/` 的 Python 实现是**验证产物**，不进发布产物、不保证兼容、不承接 issue
2. 交付形态为 **Rust 单文件二进制**（`x86_64-pc-windows-msvc` + `+crt-static`）
3. 原型的作用是**冻结行为**：它已跑通的路径（PAC 语义、CONNECT 分流、改写规则、
   Range 透传、CA 参数）在 Rust 版中必须一致，并作为对照基线

**理由**：

1. Python 交付的两个硬伤未变（ADR-009）：PyInstaller 产物杀软误报率高；运行时解包到 temp、启动 1–3 s
2. 原型已经把不可知的部分测掉了（Name Constraints 是否强制、PAC 是否被采纳、
   哈希校验是否仍生效、根证书安装是否阻塞），Rust 版只剩工程实现，没有未验证的假设
3. 原型约 580 行（`wgaccel.py` 400 + `ca.py` 182），Rust 版目标不是"更短"，
   而是把"能跑"变成"能装、能卸、能诊断"

**原型已知限制 → Rust 版处置**（来源 `prototype/README.md`，逐条对应 roadmap 阶段）：

| 限制 | 处置 |
|---|---|
| 单加速器硬编码，无健康检查与切换 | 阶段 3 实现 |
| 每连接一次请求，不支持 keep-alive | 阶段 2 实现 |
| 无线程池，未限并发 | 阶段 2 实现（限流） |
| 不处理 HTTP/2，不协商 ALPN，强制 HTTP/1.1 | 保持现状；实测 winget 接受，写入文档而不修 |
| 叶证书落盘 `certs/leaves/` | 阶段 2 改为内存生成 |
| 无 CRL/OCSP（`curl` 需 `--ssl-no-revoke`） | **不解决**，写入文档；winget/WinHTTP 不受影响 |
| ECDSA 叶证书 | 阶段 2 可改 RSA-2048 规避边缘兼容问题 |
| 安装 CA 需交互确认 | 阶段 4 按 `verification-proxy` §10 的硬要求实现 |

**不进仓库**：`prototype/.venv/`、`prototype/certs/`（含私钥）、运行日志与 stdout 捕获，
均已由 `.gitignore` 排除。原型代码入库、私钥不入库。

## ADR-016：所有加速器不可用时快速失败，不回退直连

**状态**：已采纳（2026-11-01，用户明确决定"不回退"）

**背景**：早期设计（ADR-013 派生）里有 `fallbackToOriginal`，含义是"所有加速器都不健康时
回退到原始 URL（直连 GitHub）"。当时的假设是"回退=慢一点但能下完"。

**2026-11-01 实测推翻了该假设**（同资源、同机器、前后脚测）：

| 路径 | 结果 |
|---|---|
| 直连 `curl -L` | **21 KB/s**，30 秒只收到 636,355 B，未下完 |
| 直连 `winget download`（WinHTTP） | **37 秒失败**：`WinHttpSendRequest: 12002`、`0x80072ee2`，0 字节落盘 |
| 经代理 `curl` | **724 KB/s**（1,535,063 B / 2.07 s） |
| 经代理 `winget download` | **13 秒成功**，2,544,242 B，哈希校验通过 |

关键差异在于**客户端超时策略**而不是网络是否可达：`curl` 会慢慢收，`winget` 用 WinHTTP，
37 秒就放弃。所以"回退直连"对 `winget` 不等于"变慢"，等于**多等 37 秒后仍然失败**。

**决定**：

1. 所有候选都不健康时，立刻返回 `502` 并在日志里写 `NO-HEALTHY-ACCEL`。
2. **删除 `fallbackToOriginal` 配置项**——留一个不生效的开关比没有更糟。
3. `--doctor` 用 `chain` 检查项告警"只有 1 个候选即单点"，而不是暗示有回退可用。

**代价**：

- 加速器全挂时用户直接看到失败，而不是"也许能慢慢下完"。这是有意选择：明确失败优于假死。
- 写这条 ADR 时只有 1 个可用候选；当晚复测已找到 3 个（见 verification-proxy §12），单点风险下降但未消除。

**何时重审**：若确认某类用户网络下直连确实可用（境外网络、企业专线），
可以加"直连可达性探测 + 一次性回退"——但必须先探测，不能无条件回退。
